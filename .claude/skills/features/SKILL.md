Generate the **complete** feature index for the whole codebase in one command.

Unlike `/knowledge-update --features` (which is diff-based — it only patches entries for
files that changed since the last commit), `/features` does a **full-repo enumeration**:
it discovers every feature that exists today and writes `docs/feature-index.yaml`.

## Current State

- Branch: !`git branch --show-current`
- feature-index exists: !`test -f docs/feature-index.yaml && echo "YES — will overwrite (or merge with --merge)" || echo "NO — will create"`

## Arguments

$ARGUMENTS

| Flag | Behavior |
|------|----------|
| _(empty)_ | Full rebuild — enumerate all features and overwrite `docs/feature-index.yaml`. |
| `--merge` | Keep existing hand-written entries; add only features not already listed. |

## Prerequisite (binding)

This skill reads the codebase and the existing `docs/feature-index.yaml`; it does not
build an index for you. If `docs/feature-index.yaml` is absent, this run creates it.

## Workflow

> **Navigate before you read (MANDATORY):** resolve location through the discovery ladder in [`.claude/rules/code-navigation.md`](../../rules/code-navigation.md) — feature index → glossary → architecture docs → targeted `rg`. Open raw source only for the minimum section the ladder points at, never a whole file.

### Phase 0 — Load the schema shape

Read the top of `docs/feature-index.yaml` if it exists to lock onto the existing YAML schema
(`id`, `description`, `domain_aggregate`, `entry_points`, `contract`, `repository`, `ui_api`,
`supporting`, `adr`). If it does not exist, use that same schema.

### Phase 1 — Enumerate every feature (whole repo, not a diff)

Discover all features across the codebase. Prefer the feature index; fall back to a full file scan:

```bash
# Backend entry points (controllers + use-cases) — the anchor of each feature
find server/src/presentation -name "*.controller.ts"
find server/src/application -name "*.use-case.ts"
# Frontend feature slices
find clientApp/src/features -maxdepth 1 -mindepth 1 -type d
# Contracts
find server/models/src -name "*.schemas.ts"
```

Group the results into features (one feature = one coherent user-facing capability, usually a
controller + its use-cases + the matching UI slice + its contract). Group by directory and by shared imports - files that import each other and sit under one
feature directory almost always belong to the same feature.

### Phase 2 — For each feature, extract its fields

For every feature, resolve (indexes first, source as last resort):

- **id** — short kebab-case (e.g. `ticket-crud`, `sla-manager`)
- **description** — one line, what the feature does
- **domain_aggregate** — the core domain entity/aggregate file
- **entry_points** — `controller`, `use_cases[]`, `ui_page`, `ui_component`, `ui_create`
- **contract** — the server/models path
- **repository** — `port` + `impl`
- **ui_api** — the Angular HttpClient services api slice
- **supporting** — notable helper files (optional)
- **adr** — supporting ADR ids (optional)

### Phase 3 — Write `docs/feature-index.yaml`

Assemble the full YAML with a header comment and all feature entries, grouped by domain area
with `# ── AREA ──` separators (matching the existing file's style). Paths are relative to repo root.

- **Default (no flag):** overwrite `docs/feature-index.yaml` with the freshly enumerated set.
- **`--merge`:** read the existing file, keep every current entry, and append only features whose
  `id` is not already present. Never drop a hand-authored entry.

Header to emit at the top of the file:

```yaml
# Feature Index — <Project Name>
# Each entry: description, domain aggregate/entity, primary entry-point, and implementation files per layer.
# Paths are relative to the repo root.
# Generated by /features (full enumeration).

features:
```

### Phase 4 — Report

Print a summary:

```bash
# Discovery ladder — see .claude/rules/code-navigation.md
rg -n -i '<keyword>' docs/feature-index.yaml docs/glossary.md
rg -n -i '<keyword>' .claude/planning/architecture/
rg -n '\b(class|interface|function|const|type|def|struct)\s+<Symbol>\b' server clientApp/src
rg -n '\b<Symbol>\b' server clientApp/src -l   # dependents
```

Suggest committing via `/commit` as `docs: regenerate feature-index`.

## Notes

- This is the **full-scan** counterpart to `/knowledge-update --features`. Use `/features` for a
  first-time build or a complete refresh; use `/knowledge-update --features` for incremental,
  diff-driven upkeep after a PR.
- Do **not** attempt a full semantic re-analysis from inside this skill — they are separate,
  expensive builds and must be run by the user beforehand.
